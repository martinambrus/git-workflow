Shared Drupal modules workflow

How a shared module travels from its Gitea repository to every project and customer, and how fixes made inside a project travel back. The first diagram is the developer's view; the rest is what Ops needs to build it. Everything shown ran in the pilot lab (Gitea 28.1, Packeton, a Gitea Actions runner, Drupal 11) unless the last section lists it as open.

The loop, as a developer sees it

Releases go out along the top row. Fixes made inside a project come back along the bottom row and become the next release. The main dev drives both from the developer's pull request, with two replies: /merge and /release.

System map for Ops

Every component, where it lives on the network, and which credential each connection uses. Gitea stays internal; Packeton is the only thing customers can reach.

Flow 1: release a version

Starts when the main dev has reviewed a module merge request. Ends with the release in the developer's pull request and an update pull request in every other opted-in project.

  1. Main dev

    Reply /merge activit/<module>#N

    In the developer's pull request, where the bot's comment asks for it. The bot merges the module merge request into main or 1.x once its Checks are green (while they still run, Gitea merges it as soon as they pass). Requests for changes go back to the developer, who changes the project and pushes again.
    Gitea: protected branches, pull requests only, checks required, admins tooWho: the module org's Owners team
  2. Release reminder

    Ask for the release

    After the merge the bot names the next patch version of that line in the merge request and in the developer's pull request: "reply /release activit/<module> v1.4.3". Nothing is asked for a change that only touches tests or CI files.
  3. Main dev

    Reply /release activit/<module> vX.Y.Z

    Patch for fixes, minor for compatible features, major for breaking changes or dropping a Drupal core version. The bot tags it on the project's line and refuses versions that exist, are not newer, belong to another major or would release nothing. Tagging by hand (CLI, or the web UI with the release line selected) works the same. Tags are never moved or reused.
    Gitea: protected tag pattern v*, main devs and the bot
  4. Packeton

    Index the new version

    The module repository's own webhook sends the tag to Packeton, which lists X.Y.Z within seconds. If it doesn't appear, check the webhook deliveries in Gitea, then press update on the package page.
    Trigger: per-repo webhook with composer_package_nameCredential: bot token in Packeton's auth.json
  5. Release job

    Check the tag, wait for Packeton

    Checks the tag format, that composer.json is valid and has no version key, then polls Packeton until the version is listed. Pre-release tags stop here.
    Repo: module, on tag v*Secrets: BOT_TOKEN, PACKETON_TOKEN
  6. Release job

    Deliver: into the developer's PR, update PRs elsewhere

    In the project the change came from, composer update activit/<module> runs on the developer's branch: one commit, never forced, and that pull request turns green. Every other project with the topic activit-project whose constraint allows the version gets update/<module>-X.Y.Z with vendor/ and composer.lock committed. Several open pull requests for the module, or a moved branch, fall back to an update pull request.
    Opted in: new Elmont projects; others once migrated
  7. Checks job

    Run the required checks

    No gitlinks or nested .git, no symlinks out of the project, no dev- or RC versions of activit/* on main, and no drift between vendor/ and a clean composer install with dev dependencies (package files compared; Composer's generated files checked through installed.json).
  8. Developer / reviewer

    Merge

    The developer merges their own green pull request. In other projects a reviewer reads the update's diff (it is the whole release), tests on staging (drush updb, drush cim, drush cr) and merges; update pull requests are never merged automatically.

  9. Deploy from Git

    Production pulls main. Dev-only modules are deployed but stay disabled. Rollback is a git revert of the update commit.

Flow 2: send a fix back to the module

Starts when a developer edits module code inside a project. Ends as a merge request in the module repository, which then enters flow 1.

  1. Dev A

    Edit in place, push the project branch, open the PR

    Change files under web/modules/custom/<module>/ and debug on the real site. The folder has no .git of its own, so commits go to the project. The pull request into main stays red until the change is released, and nobody can merge it before.
  2. Upstream job

    Compare each module with its locked release

    Reads composer.lock and vendor/composer/installed.json for activit/* and their locked tags, reverses the project's declared client patches, then diffs git archive of each tag against the project folder. No difference means nothing to do.
    Repo: project, on push to any branch and when a PR is opened
  3. Upstream job

    Rebuild the bot branch from the locked tag

    Cuts up/<project>/<branch> from the locked tag, applies the difference as one commit listing the project commits and authors, checks it matches the folder, then pushes it, unless an identical branch is already there. A change already merged but not released gets no second merge request.
    Target: <major>.x if it exists, else mainSecret: BOT_TOKEN
  4. Upstream job

    Open the merge request, comment in the developer's PR

    One comment: what the pull request changes, where it was sent, and the reply the main dev gives: /merge activit/<module>#N. Every further push updates the same merge request.
  5. Packeton

    Serve the bot branch as a dev- version

    The webhook covers branches too, so another project's feature branch can run composer require activit/<module>:dev-up/<project>/<branch>@dev. An RC tag with @RC is the alternative.
  6. Dev B

    Continue on the same branch

    git clone and git switch are all it takes, with no Composer or token. Their push updates the same merge request.
  7. Main dev

    Review, then /merge and /release

    Continues as flow 1, all in the developer's pull request. The release lands there as one bot commit; the developer merges it.

Flow 3: carry a fix to the newer lines

Module branches are release lines: main for the newest major, <N>.x for each older one still supported. Starts when a change is merged into an old line. Ends with it released on the newer lines, or with an issue.

  1. Forward-port job

    Cherry-pick onto the next newer line

    On every push to <N>.x: each merged change becomes a pull request into the next newer line (2.x if it exists, else main). Merging it there triggers the next hop. A change that does not apply cleanly opens an issue with the conflicting files and the commands to port it by hand, and no pull request.
    Branch: fwd/<line>/<sha>-to-<target>
  2. Main dev

    Reply /release vX.Y.Z or /merge

    The bot's prompt on the forward-port pull request names the next version of that line. /release merges it and tags the merge commit, and lists what the release contains (everything unreleased on that line). /merge only merges; a reminder then asks for /release. Changes to tests or CI files only get "nothing to release, merge it".
  3. Release job

    Update pull requests on that line

    Projects on the newer line get their normal update pull request (flow 1). Forward-porting moves code; only a release delivers it.
  4. Bot

    "Where this change went"

    The developer's pull request the change came from keeps one comment listing every hop and its state: open, merged, released as vX, already there, or does not apply cleanly. It moves to the end of the conversation whenever it changes.

Flow 4: give a customer access

External customers such as Unipo only ever talk to Packeton. Gitea has no customer organizations or accounts.

  1. Management

    Set the contract terms

    Which packages, which versions, and the support and grant dates. These are set per client and per contract and change over time.
  2. Main dev

    Create the customer in Packeton

    Settings → My groups: a group with the granted packages and a Version per package (<2.0 for the 1.x line). Settings → My users: a user without password (API only) in that group. Hand over the URL and the user's API token.
  3. Unipo

    Install with Composer

    composer config repositories.activit composer https://<packeton-host>, add the token with composer config http-basic.<packeton-host>, then composer require activit/ait_demo. They see only the granted versions; anything else is 404, and without the token 401.
  4. Packeton

    Freeze, renew

    The user's Update expiration date freezes the customer on what was released before it; their installs keep working (not Access expiration date, which locks them out). A renewal clears the date and widens the version; their project moves to a new major only when they run composer require …:^2.0.

Verified in the pilot, and still open

The pilot lab ran all of the above against Gitea 28.1, Packeton, a Gitea Actions runner, Composer and DDEV with Drupal 11: an automated end-to-end test, a full manual setup from an empty Gitea, and throwaway instances for every change to ci-tools.

  • Verified: the protection rules (no direct pushes, no forced merges of red pull requests, admins included), per-repository webhooks (tags indexed in seconds), the Checks, Upstream (from the locked tag, client patches reversed, no duplicates), the release into the developer's pull request and its fallbacks, update pull requests and their skip rules, /merge and /release with their refusals, forward-ports over two hops, conflicts as issues, the overview comment.
  • Verified: Packeton's archives leave out export-ignore files exactly like git archive; dev- versions of bot branches with slashes install; customer limits (version, update expiration, renewal) behave as flow 4 says, also behind a TLS proxy.
  • Open: the runner image from Gitea's container registry (the lab builds it locally).
  • Open: Packeton on the internet (a public certificate, rate limits, the source.url rewrite).
  • Open: speed and ergonomics on the largest real project, and runner capacity.
